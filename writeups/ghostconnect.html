2. Initial Splunk Reconnaissance

The first attempt was to search broadly for email/phishing-related activity:

index=* host="FB-WKS64"
| search email OR outlook OR phishing OR url OR attachment
| table _time User sender recipient subject url attachment

This returned approximately 19,137 events.

However, this did not mean the workstation had 19,137 email-related events.

The problem was the very broad:

| search email OR outlook OR phishing OR url OR attachment

This searches event contents and can match common words appearing in completely unrelated Windows logs.

Also, this command:

| table _time User sender recipient subject url attachment

does not create those fields. If the source event doesn't contain sender, recipient, subject, etc., Splunk simply displays them as empty.

3. Identifying the Relevant Telemetry

We then checked which sourcetypes contained the matches:

index=* host="FB-WKS64"
| search email OR outlook OR phishing OR attachment
| stats count by sourcetype
| sort - count

A large amount of the resulting data came from:

xmlwineventlog

A similar problem occurred when attempting to locate Defender events with:

index=* host="FB-WKS64"
| search Defender OR "Windows Defender" OR antivirus OR malware OR threat OR detection
| stats count by sourcetype

Again, most of the results were coming from the generic xmlwineventlog sourcetype.

This established that keyword searching alone was insufficient; we needed to inspect actual Windows Event IDs and their associated telemetry.

4. Pivoting to Sysmon Process Creation

The dataset contained Sysmon telemetry under the xmlwineventlog sourcetype.

Sysmon Event ID 1 was especially important because it records process creation.

We searched for PowerShell activity:

index=* host="FB-WKS64" sourcetype="xmlwineventlog" EventCode=1
| search Image="*powershell*" OR CommandLine="*powershell*"
| table _time User Image ParentImage CommandLine
| sort _time

This immediately reduced the noise and gave us:

  • timestamp
  • user
  • process image
  • parent process
  • command line

This was the turning point because the process tree and command lines exposed the actual execution chain.

What is it doing step-by-step?

  1. Building the Batch Script (adf.bat):

    Instead of dropping a pre-compiled tool or script onto the machine all at once, the commands use echo to write lines into a batch script (adf.bat) stored first in C:\Windows\Temp\ and later in C:\Users\chriskarma\AppData\Roaming\.

  2. Querying Active Directory Objects:

    The commands inside adf.bat use a utility named AF.exe (which stands for Active Directory Finder / a custom LDAP query tool) with filters (-f) to query the domain database for critical infrastructure details:

    • (objectcategory=computer) $\rightarrow$ Dumps a list of all domain computers into computers.txt.

    • (objectcategory=person) $\rightarrow$ Dumps a list of all domain users/accounts into users.txt.

    • (objectcategory=organizationalUnit) $\rightarrow$ Dumps the domain Organizational Units (OUs) into ous.txt.

    • (objectcategory=group) $\rightarrow$ Dumps domain security and distribution groups into groups.txt.

  3. AD enumeration was performed via a wrapper script that was iteratively re-staged in two different filesystem locations during the operation. List both full paths of adf.bat in the order they appeared.

** C:\Windows\Temp\adf.bat, C:\Users\chriskarma\AppData\Roaming\adf.bat

This investigation demonstrates how a seemingly simple phishing event can develop into a multi-stage compromise involving script execution, cloud-hosted payload delivery, endpoint reconnaissance, Active Directory enumeration, defense evasion, secondary payload deployment, persistence, data staging, and exfiltration.

The most important lesson from the hunt was that individual events were insufficient on their own. The compromise became clear only after correlating process creation, parent-child relationships, DNS, network connections, file creation, PowerShell command lines, and threat-intelligence information across the timeline.
