SigmaPredator — Windows Event Log Clearing Detection

CyberDefenders Lab: SigmaPredator
Focus: Designing and validating Sigma rules for Windows Event Log clearing across PowerShell, native CLI, WMI/WMIC, and Windows event-log telemetry.

1. Introduction

Windows Event Logs are one of the most important sources of host-level evidence during an investigation. They can record authentication activity, process execution, service activity, system changes, and other events that help analysts reconstruct an intrusion.

For an attacker, however, these logs can become a liability. Once they have obtained sufficient privileges, they may attempt to clear or remove event logs in order to reduce the evidence available to defenders. MITRE ATT&CK maps this behavior to Indicator Removal: Clear Windows Event Logs (T1070.001) in the taxonomy used by this lab. The behavior is also associated with defense evasion because it attempts to reduce investigative visibility.

The purpose of this lab is not simply to recognize that a log was cleared. The goal is to understand the different execution paths that can result in the same behavior, identify the telemetry produced by each path, and then translate those observations into Sigma rules that can be validated against historical Windows event data with Chainsaw.

The investigation therefore follows this model:

                 Windows Event Log Clearing
                           |
        +------------------+------------------+
        |                  |                  |
      CLI                WMI/WMIC          PowerShell
        |                  |                  |
    wevtutil         NTEVENTLOG alias   Cmdlets / .NET APIs
        |                  |                  |
   Process creation   Process creation    Script Block Logging
      / Sysmon              / WMI              Event ID 4104
        |                  |                  |
        +------------------+------------------+
                           |
                  Windows Event Log artifacts
                      Event ID 104 / 1102
                           |

                           |
                        Chainsaw

The remainder of this write-up builds that map from the ground up.

2. Part I — Research and Detection Planning

Before writing a Sigma rule, the first step was to determine which native Windows mechanisms an attacker could use to clear event logs and, more importantly, what evidence each mechanism would leave behind.

The main paths investigated were:

Technique / MechanismExecution layerUseful telemetryMain artifact used in the lab
wevtutilNative Windows CLIProcess creation / command lineSysmon Event ID 1
wmic + NTEVENTLOGWMI through WMICProcess creation and WMI-related activitySysmon Event ID 1 / WMI artifacts
PowerShell cmdletsPowerShellScript Block LoggingPowerShell Event ID 4104
PowerShell .NET APIsPowerShell / .NETScript Block Logging where applicableEvent ID 4104
Event log actually being clearedWindows Event LogSecurity/System eventsEvent ID 1102 / 104

This distinction is important. A detector can look for the attempt to clear a log, such as a process executing wevtutil, or for the result of the operation, such as Event ID 1102 indicating that the Security log was cleared.

That difference is the foundation of the three Sigma rules used later in the lab.

3. Understanding wevtutil

3.1 What is wevtutil?

wevtutil.exe is a native Windows command-line utility for managing the Windows Event Log system. Microsoft documents it as a tool that can query logs, retrieve provider information, export logs, configure logging, and clear event logs. It is included in %windir%\System32.

For detection engineering, wevtutil is particularly interesting because it is a legitimate Microsoft-signed utility that can be abused for defense evasion. This is a classic example of a dual-use binary: the presence of the executable itself is not malicious, but a command such as clear-log is highly relevant when investigating possible log tampering.

3.2 The clearing operation

The important subcommand for this lab is:

wevtutil cl <LogName>

cl is the short form of clear-log. Microsoft documents it as clearing events from the specified event log, with an optional /bu parameter that can back up the events before clearing them.

For example, the technique can target the standard Windows logs:

wevtutil cl System
wevtutil cl Application
wevtutil cl Security

The exact syntax is less important for detection than the combination of:

wevtutil + clear-log / cl + target log

That combination gives us much stronger detection logic than simply alerting on wevtutil.exe.

3.3 Why wevtutil is useful to a defender

The advantage of detecting wevtutil at the process level is that the detector can fire on the attacker's attempt, potentially before the defender sees the resulting clearing event.

The disadvantage is that wevtutil has many legitimate administrative uses. Therefore, a mature detection should not alert on the executable alone. It should anchor on the specific destructive subcommands and, ideally, the binary identity as well.

3.4 Comparison with the other approaches

MethodMain advantageMain limitation
wevtutilNative, simple, command line is highly visible in process telemetryLegitimate administrative use creates potential false positives
WMIC/WMIAlternative management path; can blend into normal WMI administrationMore indirect and can be harder to interpret from a single event
PowerShellRich scripting capability and multiple APIs/cmdletsRequires useful PowerShell telemetry, especially Script Block Logging
Event ID 104/1102Direct evidence that a log was actually clearedIt tells us the effect occurred, not necessarily which process caused it

This already suggests a defense-in-depth approach: detect the execution path and also detect the resulting log-clearing event.

4. WMI, WMIC, and the NTEVENTLOG Class/Alias

4.1 What is WMI?

Windows Management Instrumentation (WMI) is Windows' management infrastructure for interacting with system objects and administrative functionality through a common programming and management interface.

Unlike a simple executable such as wevtutil, WMI is an abstraction layer. A program can query or invoke operations through WMI classes rather than directly manipulating the underlying resource.

This matters for detection because attackers can use WMI to perform actions without relying exclusively on the most obvious command-line utilities.

4.2 What is WMIC?

WMIC (Windows Management Instrumentation Command-line) is a command-line interface to WMI. Historically, it allowed operators to interact with WMI classes directly from the command line.

For this lab, the important distinction is:

WMI       = the Windows management infrastructure
WMIC      = a command-line interface to WMI
NTEVENTLOG = the WMIC alias used for the Windows event-log WMI class

So when the lab asks which WMI class is involved, the precise terminology is important: the WMIC alias is NTEVENTLOG, while the underlying WMI class is Win32_NTEventLogFile. Microsoft documents Win32_NTEventLogFile as representing the logical file/directory associated with an operating system event log.

4.3 Why NTEVENTLOG matters for detection

A WMIC command can use the event-log WMI class and invoke the clearing operation against a selected log. In a process-creation record, this may appear as a command line similar to:

wmic nteventlog where "LogFileName='System'" cleareventlog

The important observation is that the attacker is not using wevtutil at all. The underlying objective is identical, but the execution path is different.

That is exactly why a detector based only on wevtutil.exe is incomplete.

4.4 Comparing WMI with wevtutil

wevtutil.exe
    |
    +--> clear-log

wmic.exe
    |
    +--> NTEVENTLOG / Win32_NTEventLogFile
            |
            +--> ClearEventLog

This distinction becomes important later when we explicitly try to detect native CLI clearing while excluding WMI-based clearing.

5. PowerShell Detection

PowerShell provides several ways to manipulate Windows event logs. For this lab, the important question is not only which command can clear a log, but which PowerShell telemetry allows us to recover that command from historical evidence.

5.1 Script Block Logging and Event ID 4104

The required PowerShell logging channel is Script Block Logging.

When Script Block Logging is enabled, PowerShell records the content of processed script blocks in the PowerShell Operational event log. The relevant event is Event ID 4104. Microsoft documents Event ID 4104 as the Script Block Logging event.

For a detection engineer, this is extremely valuable because the event can contain the actual PowerShell statement that an attacker executed, rather than only indicating that powershell.exe started.

powershell.exe
      |
      +--> Script Block Logging
              |
              +--> Event ID 4104
                      |
                      +--> ScriptBlockText

That ScriptBlockText field becomes the main field used in the first Sigma rule.

5.2 PowerShell cmdlets used for log clearing

The two built-in PowerShell cmdlets relevant to the lab are:

Clear-EventLog

Clear-EventLog clears entries from the specified event logs. Microsoft documents that it can operate against local or remote computers and requires appropriate administrative privileges.

Clear-EventLog -LogName System

Remove-EventLog

Remove-EventLog is another native PowerShell EventLog cmdlet, but it is important to distinguish it from Clear-EventLog: Clear-EventLog directly deletes the entries from a specified classic event log, while Remove-EventLog is used to remove an event log and its associated event sources.

For this lab, both names are therefore useful strings to search for in PowerShell Script Block Logging.

5.3 Native .NET APIs

PowerShell can also access .NET functionality instead of relying exclusively on a cmdlet. Relevant APIs include methods exposed through the following namespaces:

System.Diagnostics.Eventing.Reader.EventLogSession.ClearLog
System.Diagnostics.EventLog.Clear

This creates another detection challenge. A detector that only searches for Clear-EventLog and Remove-EventLog could miss an attacker who invokes the underlying API from PowerShell.

However, the lab explicitly states that PowerShell is running in Constrained Language Mode and instructs the rule to disregard .NET binaries. That constraint is why the practical detection rule focuses on the observable command strings rather than building a .NET-specific condition.

6. Detecting the Result: Event IDs 104 and 1102

The previous sections focused on detecting the action that performs log clearing. Windows also provides telemetry for the result of that action.

Two event IDs are especially important:

Event IDTypical logMeaning
104SystemThe Windows Event Log service reports that a log was cleared
1102SecurityThe Security audit log was cleared

This creates an important distinction:

Process / PowerShell telemetry
        |
        +--> tells us HOW the attacker attempted the action

Event ID 104 / 1102
        |
        +--> tells us that the log-clearing effect occurred

For incident response, the second category is often extremely high-value because it provides direct evidence of log tampering. For threat hunting, the first category can be even more useful because it may reveal the operator's command, process, user, parent process, and execution context.

The practical consequence is that there is no single perfect telemetry source.

A robust defensive strategy combines:

  1. Execution telemetry — catches the attempted technique.
  2. Script Block Logging — exposes PowerShell content.
  3. Process creation — exposes native CLI/WMI invocation and command-line context.
  4. Windows event-log clearing events — confirms the actual effect.

8. Part II — Sigma Rule Development and Validation

8.1 What is Sigma?

Sigma is a generic detection-rule format designed to describe suspicious log activity in a platform-independent way.

The main idea is to separate the detection logic from the specific SIEM query language. A Sigma rule can then be translated into a query suitable for different platforms.

The general structure is:

title:
    ...

id:
    ...

status:
    ...

description:
    ...

logsource:
    ...

detection:
    ...

level:
    ...

tags:
    ...

The most important part operationally is the relationship between selection and condition.

For example:

detection:
  selection:
    EventID: 4104
    ScriptBlockText|contains:
      - 'Clear-EventLog'
      - 'Remove-EventLog'
  condition: selection

The contains modifier tells Sigma to search the selected field for any of the specified strings. The list therefore behaves as a set of alternatives inside that field, while the surrounding fields must also match.

9. Question 1 — PowerShell Event Log Clearing

9.1 Task interpretation

The first detection exercise asked for a Sigma rule that detects event-log clearing through PowerShell Script Block Logging and then validates the rule against the historical logs with Chainsaw.

The lab also provides an important constraint:

PowerShell is operating in Constrained Language Mode, so the rule should disregard .NET binaries.

The useful telemetry is therefore:

Log source       = Windows PowerShell
Event ID         = 4104
Important field  = ScriptBlockText
Behavior         = event-log clearing commands

9.2 Rule used

title: PowerShell Event Log Clearing
id: 1235678-1234-1234-1234-123456789abc
status: testing
description: Detects Windows Event Logs deletion through ScriptBlock Logging (Event ID 4104) while ignoring .NET binaries due to Constrained Language Mode constraints.
logsource:
  product: windows
  service: powershell
detection:
  selection:
    EventID: 4104
    ScriptBlockText|contains:
      - 'Clear-EventLog'
      - 'clear-eventlog'
      - 'Remove-EventLog'
      - 'remove-eventlog'
      - 'wevtutil'
  condition: selection
level: high
tags:
  - attack.defense_evasion
  - attack.t1070.001

9.3 Breaking down the rule

logsource

logsource:
  product: windows
  service: powershell

This tells the detection engine that the rule is intended for Windows PowerShell telemetry rather than generic Windows events.

Event ID selection

EventID: 4104

This restricts matching to PowerShell Script Block Logging events.

Script content matching

ScriptBlockText|contains:
  - 'Clear-EventLog'
  - 'clear-eventlog'
  - 'Remove-EventLog'
  - 'remove-eventlog'
  - 'wevtutil'

The rule searches the actual script contents for commands associated with the clearing behavior.

condition

condition: selection

This means the event must satisfy the entire selection. Within the ScriptBlockText|contains list, matching any one of the listed values is sufficient, while the event must also be Event ID 4104.

Severity and ATT&CK mapping

level: high

tags:
  - attack.defense_evasion
  - attack.t1070.001

A log-clearing action is high-value defense-evasion telemetry, especially when the action targets the Security or System logs.

11. Question 2 — Native CLI Detection with Sysmon

11.1 Task interpretation

The second exercise changes the detection perspective. Instead of looking inside PowerShell, the objective is to detect native command-line event-log clearing utilities, such as wevtutil, using process-creation telemetry.

The task specifically excludes WMI and allows Sysmon as a telemetry source.

That changes the hunting model from:

PowerShell content -> Event ID 4104

to:

Process execution -> Sysmon Event ID 1 -> CommandLine

11.2 Rule used

title: Event Log Clearing via Sysmon Process Creation
id: 87654321-4321-4321-4321-9abcdef12345
status: testing
description: Detects the execution of the wevtutil utility to clear event logs via Sysmon Process Creation (Event ID 1).
logsource:
  product: windows
  service: sysmon
detection:
  selection:
    EventID: 1
    CommandLine|contains:
      - 'wevtutil'
      - ' cl '
      - 'clear-log'
  condition: selection
level: high
tags:
  - attack.defense_evasion
  - attack.t1070.001

11.3 Why Sysmon Event ID 1 is useful

Sysmon Event ID 1 records process creation information. In the observed event, Chainsaw exposed fields including:

Image:            C:\Windows\System32\wevtutil.exe
OriginalFileName: wevtutil.exe
CommandLine:      wevtutil clear-log Security
ParentImage:      C:\Windows\System32\cmd.exe
User:             DESKTOP-6I5AMEJ\Marc
IntegrityLevel:   High

This is significantly richer context than a simple string match. The defender can potentially identify:

  • which executable ran;
  • which command was supplied;
  • who ran it;
  • which parent process launched it;
  • whether the process was elevated;
  • and when it occurred.

That makes process creation a particularly useful telemetry source for native utility abuse.

12. Why the WMI Exclusion Matters

The task specifically asks for native CLI clearing while excluding WMI. This is an important detection-engineering problem because the same underlying behavior can appear under different process names.

For example:

wevtutil clear-log Security

and:

wmic nteventlog where "LogFileName='System'" cleareventlog

both pursue event-log clearing, but the first is native wevtutil execution while the second is a WMI/WMIC path.

A detector that only searches for generic strings such as clear, cl, or clear-log can therefore become too broad.

The lab hint specifically recommends anchoring on both the binary identity and the destructive sub-command:

wevtutil identity
        AND
clear-log / cl destructive intent

Important validation note

The rule used during the exercise was intentionally simpler and still produced the requested latest timestamp from the supplied dataset. However, the raw Chainsaw output also showed a wmic.exe match at 2025-04-28 09:19:35 because the current CommandLine|contains logic is broader than a strict wevtutil.exe identity check.

Therefore, the rule worked for the observed answer, but it is not as tightly scoped as the lab hint recommends. In a production detection, I would strengthen it by requiring wevtutil.exe/its original filename together with clear-log or the cl subcommand, and explicitly excluding wmic.exe when the backend supports that reliably.

This is a useful lesson: a rule can produce the expected challenge answer while still leaving room for precision improvements.

14. Question 3 — Detecting the Clearing Event Itself

14.1 Task interpretation

The final exercise moves one layer lower. Instead of detecting the process or script that attempted to clear a log, the task asks for a Sigma rule that identifies the Windows events generated when the clearing actually occurs.

The two target events are:

104  -> System log cleared
1102 -> Security audit log cleared

This is a classic result-based detector.

14.2 Initial mistake

My first attempt used a Security-only log source:

logsource:
  product: windows
  service: security

This produced no useful result because Event ID 104 is associated with the System log, while Event ID 1102 is associated with the Security log.

This failure was instructive: the event ID alone is not enough. The log source must match the location where the event is actually generated.

The corrected approach is to use a Windows-wide log source capable of matching both event IDs.

14.3 Rule used

title: File Deletion Detection - Event Log Clearing
id: 1235678-1234-1234-1234-123456789abc
status: testing
description: Detects when a Windows Event Log channel is cleared by tracking Event IDs 1102 and 104.
logsource:
  product: windows
detection:
  selection:
    EventID:
      - 1102
      - 104
  condition: selection
level: high
tags:
  - attack.defense_evasion
  - attack.t1070.001

14.4 Why this rule is different from the first two

The previous rules tried to identify how the attacker performed the action:

PowerShell ScriptBlockText
            OR
Sysmon process + command line

This rule instead identifies the effect:

Event ID 104 or Event ID 1102

That gives it a very different detection profile. It can catch clearing regardless of whether the attacker used wevtutil, WMIC/WMI, PowerShell, Event Viewer, or another native or third-party mechanism.

The trade-off is that it provides less information about the original execution method.

15. Chainsaw Result for Question 3

After correcting the log-source mistake and searching the historical collection, the earliest matching event was:

2019-01-20 07:00

This result reinforces why the log-source definition is part of the detection logic itself. Searching only the Security channel would have missed System Event ID 104 entirely.

16. Comparing the Three Sigma Rules

The three rules are complementary rather than interchangeable.

A useful way to think about them is:

                    Detection coverage
                           |
          +----------------+----------------+
          |                |                |
       PowerShell        Process          Result
          |                |                |
       Event 4104       Sysmon 1       Event 104/1102
          |                |                |
      "What script?"   "What ran?"    "Did clearing occur?"

This is why using several detection layers is preferable to relying on one signature.

17. Detection Engineering Lessons

17.1 Detect behavior, not just filenames

A filename such as wevtutil.exe is not inherently malicious. The destructive intent is much clearer when the binary is combined with commands such as:

clear-log
cl

The same principle applies to PowerShell: finding powershell.exe is much less valuable than finding a 4104 event containing Clear-EventLog.

17.2 The same ATT&CK behavior can have many execution paths

wevtutil.exe
wmic.exe -> NTEVENTLOG
PowerShell -> Clear-EventLog
PowerShell -> Remove-EventLog
PowerShell -> .NET EventLog APIs
Event Viewer / other mechanisms

A detection program should therefore map the behavior to multiple telemetry sources rather than searching for one command.

17.3 Telemetry configuration is part of detection quality

The PowerShell rule only works because Script Block Logging provides Event ID 4104. The process-creation rule depends on process telemetry such as Sysmon Event ID 1. The final rule depends on Windows generating and retaining Event IDs 104 and 1102.

A perfect Sigma query cannot recover telemetry that was never collected.

17.4 Context improves precision

The lab's Sysmon exercise demonstrated this especially clearly. Searching for generic command fragments can match unrelated tools. Stronger rules should combine:

Binary identity
      +
Destructive sub-command
      +
Relevant arguments

17.5 Result-based and action-based detections should coexist

A process-based rule may catch the attacker's command, while Event ID 104/1102 confirms the effect. Correlating both can give a much stronger incident signal than either one alone.

Sysmon 1: wevtutil clear-log Security
                 |
                 v
Security 1102: audit log was cleared

That sequence gives the analyst both the actor's action and the resulting system state.

20. Conclusion

The SigmaPredator lab demonstrates an important detection-engineering principle: defense evasion techniques should be modeled from multiple angles.

wevtutil, WMIC/WMI, and PowerShell provide different ways to reach the same objective. PowerShell Script Block Logging can expose the exact script content, Sysmon process creation can reveal the executable and command line used to perform the action, and Event IDs 104 and 1102 can provide direct evidence that a Windows log was actually cleared.

The Sigma rules developed during the lab translate those observations into portable detection logic, while Chainsaw provides a practical way to validate the rules against historical Windows event data. The validation process also exposed an important reality of detection engineering: a rule can technically match the intended behavior while still being broader than desired. The wmic.exe match in the Sysmon exercise is a good example of why binary identity, command context, and telemetry scope must be considered together.

Ultimately, the strongest detection strategy is not a single rule. It is a layered model in which process activity, script content, and security-relevant outcomes reinforce one another.
