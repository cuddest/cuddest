Deputy's Ledger

The first page was just a briefing. It gave me two accounts:

analyst:hunting4bugs
guest:guest123

Both were described as normal members of one organization, and the challenge explicitly said that no admin account existed anywhere. That last sentence was almost an instruction: I was probably supposed to make one.

Recon

/api exposed the application's endpoint list:

{
  "endpoints": [
    "/api/login",
    "/api/whoami",
    "/api/ledger/<org_id>/records",
    "/api/ledger/<org_id>/master",
    "/api/ledger/<org_id>/members/<username> [PATCH]",
    "/graphql"
  ]
}

Logging in as analyst returned a JWT with RS256 and org_id: acme. The master ledger endpoint returned forbidden because it required the admin role.

Creating an Admin

The member-management endpoint immediately stood out. It was supposed to edit a member, but there was no restriction preventing me from editing myself and no allowlist for which fields could be changed.

curl -X PATCH .../api/ledger/acme/members/analyst \
  -H "Authorization: Bearer $T" \
  -d '{"role":"admin"}'

The response confirmed the role change. Now the master ledger endpoint opened. Unfortunately, it did not contain the flag — only an internal reserve note. acme was not the target organization.

GraphQL

The /graphql endpoint had introspection enabled. The internalDirectory field exposed:

orgs
users
signingKeyPem

This revealed a second organization (globex), a user named director, and the RSA public key used to verify JWTs.

RS256 to HS256 Algorithm Confusion

The server was verifying RS256 tokens, and I now had the public RSA key. The classic algorithm-confusion attack was possible.

I created a token with HS256 and payload { "sub": "director", "org_id": "globex" }, using the raw PEM bytes as the HMAC key. The trailing newline had to remain intact — the first time I stripped it, signature verification failed.

With the PEM preserved byte-for-byte, the forged token was accepted.

Escalating Again

The same unsafe PATCH endpoint was still there. This time I targeted the Globex account:

curl -X PATCH .../api/ledger/globex/members/director \
  -d '{"role":"admin"}'

The role changed to admin. The master ledger endpoint finally opened.

What made this challenge interesting was that there were really two independent authorization failures chained together. The PATCH endpoint broke the role boundary inside an organization. The JWT algorithm confusion then broke the organization boundary itself.
