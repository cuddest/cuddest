Ledger Bloom

This challenge looked simple at first. The page had some flavor text and one number called Current Yield. There were no forms, no obvious parameters, and almost nothing to click.

Then I noticed three notes in the sidebar:

Ephemeral computation seed loaded into memory for every fresh session
Character filtering remains intentionally narrow to preserve compatibility
Long recipes are discarded by the allocator when the byte budget is exceeded

And at the bottom:

Source visibility remains available through the existing diagnostic route.

That was enough to make me start looking for source disclosure and some kind of constrained expression evaluator.

First Look at the Application

The response headers included a Flask session cookie. The middle section was just base64, so I decoded it:

{
  "ingredient": {
    " b": "dXh4endkZmhsZg=="
  },
  "measurements": {
    " b": "NTUrMjk="
  }
}

The decoded values were:

ingredient = uxxzwdfhlf
measurements = 55+29

The page showed the result of 55+29, so the next question was obvious: what happens between those two session values and the result shown in the browser? It turned out the server was constructing code from them.

One detail I noted and then ignored for far too long was the { " b": ... } wrapper. That is Flask's tagged representation for bytes, not an ordinary string. That detail later became the key to the entire solve.

Finding the Source

The challenge explicitly mentioned a diagnostic route, so I tried the usual guesses:

/source
/src
/debug

/debug returned the source. The relevant code was:

def calc(recipe):
    global garage
    builtins, garage = {"__builtins__": None}, {}
    try:
        exec(recipe, builtins, garage)
    except Exception:
        pass

And later:

recipe = "%s = %s" % (ingredient, measurements)

followed by a very small blacklist:

[ , ( , _ , .

The application was effectively implementing a small Python jail around exec.

Mapping the Jail

There were five important constraints.

1. Hardcoded Flask secret fallback

If SECRET_KEY was not configured, the application used a hardcoded fallback key. That meant I could potentially sign my own Flask session cookie and control both values that make up the expression.

2. Byte budget

The generated recipe had to be at least 20 characters long, and anything longer than 300 characters was rejected.

3. Four banned characters

[
(
_
.

4. Empty builtins

The code executed with {"__builtins__": None} so normal builtins such as print, open, __import__ were unavailable.

5. The execution path was blind

The branch that executed my recipe returned a normal template without exposing the value produced by exec.

Confirming the Secret Key

I reproduced Flask's cookie serializer using the fallback key and confirmed the key by sending an intentionally blocked value — the blacklist itself became an oracle.

Getting Feedback From a Blind Jail

Because successful execution produced no output, I built a timing oracle:

zzzzzzzzzz = 1234567890   → 0.21s
zzzzzzzzzz = 9**9**7      → 1.59s

The second request was clearly slower, which proved code execution.

The Real Environment: Python 2

Once I had a foothold, I checked the runtime environment: PYTHON_VERSION=2.7.18. The container was launching the application with Python 2.7.

In Python 2:

  • str is bytes
  • the %s = %s operation therefore produces a byte string
  • exec on a byte string honors the encoding declaration at the beginning of the source

The code looked like Python 3 code, but the interpreter running it was Python 2. That was the branch that should not have existed.

Bypassing the Character Filter With an Encoding Declaration

Because the blacklist only inspected the raw bytes, I could encode forbidden characters so they were not physically present in the payload. The trick was to start the byte-string source with:

#coding:unicode-escape

Then a byte sequence such as \x28 would be decoded by the compiler into ( before the Python parser tokenized the source. The blacklist saw \ x 2 8 while the compiler saw (.

Reaching the Application's Real Globals

A generator expression gives access to its own frame through gi_frame, and the frame chain eventually reaches the caller's globals:

global g
g=(g.gi_frame.f_back.f_back.f_globals for i in "1")
for G in g:
    pass
G["session"]["z"]=G["os"].popen("id").read()

That transformed the blind jail into a readable command-execution primitive. The returned session cookie contained:

uid=1337(ctf) gid=1337(ctf) groups=1337(ctf)
/app

Full Chain

Flask session manipulation
        ↓
Hardcoded SECRET_KEY fallback
        ↓
Python eval/exec primitive
        ↓
Blind execution → Timing oracle
        ↓
Python 2 byte-string behavior
        ↓
PEP 263 encoding bypass
        ↓
Frame/global namespace escape
        ↓
Session-based output channel
        ↓
Command execution → Flag

The most interesting part was that the final bypass had very little to do with the obvious blacklist. The real bug was the mismatch between what the code looked like it expected to run and what interpreter was actually running it.
