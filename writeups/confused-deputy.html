Confused Deputy

The challenge started with a simple briefing page. There were two normal logins, guest and analyst, and the page explicitly said that no admin account existed.

That last line was suspicious enough to make the objective pretty clear: I was probably supposed to create one.

Recon

I checked /api, which exposed the relevant endpoints:

login
whoami
admin
debug

Logging in as analyst returned a JWT. I decoded it and found:

{
  "alg": "RS256",
  "role": "user"
}

The admin endpoint required the role to be admin, so the first question became: where does the application get the key it uses to verify the JWT?

Finding the Public Key

Because the token used RS256, I looked for the public key and eventually found it at:

/.well-known/jwks.json

The endpoint exposed the RSA public key in PEM form. Normally that is exactly what you want. A public key is supposed to be public.

The problem appears when an application allows the algorithm in the JWT header to decide how the signature should be verified.

RS256 to HS256 Algorithm Confusion

RS256 is asymmetric. The server signs with a private RSA key and verifies with the corresponding public key.

HS256 is symmetric. The same secret is used to sign and verify.

If the verification code accepts both algorithms and simply trusts the alg value from the token header, an attacker can change RS256 to HS256 and make the server interpret the public RSA key as an HMAC secret.

I built a new token with HS256 as the algorithm and role: admin in the payload, using the exposed PEM bytes as the HMAC key.

The first attempt failed because I stripped the trailing newline from the PEM file. That tiny detail mattered — the signature is calculated over the exact key bytes.

Once I preserved the PEM byte-for-byte, the forged token was accepted.

Flag

africc{alg_confusion_3v3rywh3r3}

Full Chain

JWT with RS256
      ↓
Find public verification key
      ↓
Change alg to HS256
      ↓
Sign with public key bytes
      ↓
Server accepts forged token
      ↓
Admin role → Flag

The core security mistake is not that the public key was exposed. The real problem is the trust placed in the token's requested algorithm. A secure implementation should pin the allowed algorithm and never treat a public verification key as a valid HMAC secret.
