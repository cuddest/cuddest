Conti — Investigating a Compromised Exchange Server

Overview:

This fun, medium diffuculty ranked room on TryHackMe simulate an investegation on a compromised Exchange server ( Microsoft Exchange Server is an entreprise-level messaging and collab server, where you can send emails, shedule meetings and tasks, save contacts and communicate on the entreprise level securily).

We are going to use Splunk (Cisco's solution for analyzing, searching and monitoring huge amounts of data in real time, used mainly as SIEM (Security Information and Event Management)).

After joining the room and connecting to openvpn you can access the room by the URL provided or through the attackbox, to face the famous splunk interface !

We navigatge to Search & Reporting, filter by All Time, and of course, our first search is going to be index=*, just to make sure everything is ready , and boom : 28,145 events. READY TO GO :))

  1. Can you identify the location of the ransomware? (HINT:Look for a common Windows binary located in an unusual location.)

Ransomware operators use names that look like legitimate windows programs (eg: svchost.exe...), to trick administrators when checking task manager, but we still can check its legitimaty by checking the spelling, path, parent process ect...

We gonna use this splunk querie:

index=* host="*win-aoqkg2as2q7*" (EventCode=1 OR EventCode=4688) (Image="*\\svchost.exe" OR Image="*\\cmd.exe" OR Image="*\\rundll32.exe" OR Image="*\\explorer.exe" OR Image="*\\taskhostw.exe" OR Image="*\\notepad.exe" OR Image="*\\regsvr32.exe" OR Image="*\\lsass.exe")
| search NOT (Image="*\\Windows\\System32\\*" OR Image="*\\Windows\\SysWOW64\\*" OR Image="*\\Windows\\explorer.exe")
| table _time, ParentImage, Image, CommandLine

Here we are :
- filtering by the host win-aoqkg2as2q7*
- looking for events with EventCode 1 or 4688 ( Windows Security Event ID are codes that help us understand what a specific event that was recoreded by Windows Event Log system represent , based on the code we can specify what was the event for. ( Windows Event Log system is a built-in events recoreder into all windows system that helps monitor and troubleshoot systems ))
- We asked Splunk to look for a list of very common, legitimate Windows programs (like cmd.exe, svchost.exe, explorer.exe).
- We then used the NOT command to tell Splunk: "Ignore anything running from C:\Windows\System32\ or C:\Windows\SysWOW64\" (which are the only places those legitimate files should ever live).

and GOTCHA !

C:\Users\Administrator\Documents\cmd.exe

2.What is the Sysmon event ID for the related file creation event?

Sysmon is part of the powerfull system utilites Sysinternals suite, a strong, details oriented logging tool with extra feature that native logging tools may miss.

like Windows Event Log, symson works with IDs to classify events, googling what is the ID of a creation event in symson, we get the answer easily.

11

3.Can you find the MD5 hash of the ransomware?

oh yes we can, so since we have the image location of the ransomware, we can utilize that to search for any hashes using the Hashes field in our queires:

index=* host="*win-aoqkg2as2q7*" source="*Sysmon*" EventCode=1 Image="C:\\Users\\Administrator\\Documents\\cmd.exe"
| table _time, Image, Hashes

et voilaaaa :

290c7dfb01e50cea9e19da81a781af2c

4.What file was saved to multiple folder locations?

Since we know the full path of where the ransomware resides, we can utilize that to find all the files it dropped around, not just that, but splunk allows us to rank these files by their count of appearance !

Using :

index=* host="*win-aoqkg2as2q7*" source="*Sysmon*" EventCode=11 Image="C:\\Users\\Administrator\\Documents\\cmd.exe"
| eval FileName=mvindex(split(TargetFilename,"\\"),-1)
| stats count by FileName
| sort - count

We are:
- searching through sysmon all the events of creation (EventCode 11) where the parent image is cmd.exe, our ransomware.

and tarra ! there is only one result, created 18 times.

readme.txt

5.What was the command the attacker used to add a new user to the compromised system?

persistence time now huh?

Well we know as a fact that if a hacker intended to create a new user account, he would type something like :

net user hacker account Password123!

so we will use :

index=* host="*win-aoqkg2as2q7*" (EventCode=1 OR EventCode=4688) CommandLine="*net *user */add*"

| table _time, User, ParentImage, Image, CommandLine

So we can :
- Filter by creation events ( 1 for sysmon and 4688 for windows security log)
- look for any command simmilair to the user creation command.

and wow, we found it !

net user /add securityninja hardToHack123$

6.The attacker migrated the process for better persistence. What is the migrated process image (executable), and what is the original process image (executable) when the attacker got on the system?

okay, first, we start with our hint, Event ID 8, mhm, a quick google search will help us understand that this id is for CreateRemoteThread event, this action exists to enable the injection of a thread from process A inside another process B memory ( and i know, why something like this exists? oh well some debuggers or antivirus use it so they get access to the memory of a process to enable better analyzing).

so now that we have a basic understanding of what we have, we can use this query:

index=* host="*win-aoqkg2as2q7*" source="*Sysmon*" EventCode=8
| table _time, SourceImage, TargetImage

to filter all EventCode=8 events.

the results were fabulous !

Here we found two results, the first, time sense, is metigating from the beacon powershell process into this illigitimate created process unsecapp.exe ( you can notice that the path is illigitmate).

and the second is metigating from the just created process into the legitimate windows process lsass.exe, which we will dive into later.

but since the question is looking for the first mitigation. our answer is clear!

C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe,C:\Windows\System32\wbem\unsecapp.exe

But that is not our job now, our job is to notice that this tree have a familliar process, you guessed it ? yes exactly ! lsass.exe, the one we saw the last question !

This process handles security and authentication:

  • User login validation

  • NTLM / Kerberos

  • Token generation

It is a very sensitive process:

  • Credential dumping tools (like Mimikatz) target it.

so yeah, it is where system hashes resides, and the attacker used it to inject a thread using CreateRemoteThread, then access its memory to dump hashes.

From the last question query result, we can extract our answer!

8.What is the web shell the exploit deployed to the system?

First, we know that Microsoft Exchange runs on a software called ISS, that handles all the traffic, it uses ASP.NET, so based on these infos, we can filter all the web traffic based on these two informations, plus the hint given to us to filter by POST request, which will help a lot since malware developers love to use POST to hide their payloads in the body so logs dont catch it.

index=* host="*win-aoqkg2as2q7*" sourcetype="*iis*" cs_method="POST" cs_uri_stem="*.aspx"

and we end up with these four delicious results:

we can clearly see the name of the webshell deployed in the url.

i3gfPctK1c2x.aspx

9.What is the command line that executed this web shell?

Well my first thought here was, since we have the name of the webshell, why dont we just look in sysmon logs and filter by its name and EventCode 11 ( creation id), using something that looks like this:

index=* host="*win-aoqkg2as2q7*" sourcetype="*Sysmon*" EventCode=11 TargetFilename="*i3gfPctK1c2x.aspx"

but this one failed, which was weird.

after being stuck for sometime, i tried to look for any sysmon log that mention the filename, using something like this:

index=* sourcetype="*Sysmon*" host="*win-aoqkg2as2q7*" "i3gfPctK1c2x.aspx"
| table _time, sourcetype, EventCode, _raw

And to my surprise, IT WORKED !

after some reflection and research, the only logical conclusion that i came into of why the first failed and the second worked was because Administrators often configure Sysmon to ignore File Creation events (Event 11) in highly active directories like C:\inetpub\ (the web server folders) because it generates too much noise and wastes storage. Because the event was never logged by the system, our highly specific query failed.

attrib.exe -r \\\\win-aoqkg2as2q7.bellybear.local\C$\Program Files\Microsoft\Exchange Server\V15\FrontEnd\HttpProxy\owa\auth\i3gfPctK1c2x.aspx
