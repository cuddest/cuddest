Summit Supply

Solving this challenge felt like Troy's war. Getting the flag out of the box at the end was basically Odysseus trying to make it home.

Recon

The application was split into three services behind one Nginx instance. One header caught my attention immediately:

Service-Worker-Allowed: /challenge/

The session was a JWT containing id, exp, and antiCSRFToken. The session cookie was not marked HttpOnly, which immediately made it worth testing for client-side exposure.

Once logged in, the application exposed a small marketplace with three interesting features: adding a new item, viewing product pages, and reporting a listing to a bot.

The Note Field

The interesting code on product pages looked like this:

let note = `USER CONTENT`;
const clean = DOMPurify.sanitize(note, {
    FORBID_ATTR: ['id', 'style'],
    USE_PROFILES: {html: true}
});
document.getElementById('note').innerHTML += clean;

The application inserted the user value directly into a JavaScript template literal before DOMPurify ran. Backticks were stripped, <, > and & were encoded, but ${C} survived. This was not HTML injection — it was JavaScript expression interpolation.

Turning the Bot Into a Browser Oracle

Instead of trying to force the bot to exfiltrate to an external server, I used the application itself as the communication channel. I created a product whose description contained whatever I wanted to steal, made the bot visit it, then read that same product back through my normal authenticated session.

The first test was document.cookie. The response contained the session cookie including the JWT. The decoded token belonged to id: 1 — the bot was the administrator.

The Real Second Bug: File Upload Path Traversal

The contract upload endpoint did not sanitize the multipart filename. I tested:

../static/js/pwn2.js

and the file was written into the application's static directory. The response messages gave me a small write oracle: Contract Added meant success, Invalid PDF! meant content failed validation.

Bypassing the PDF Validation

The validator did not care about what came after the end of the PDF. So the strategy was: valid PDF + extra attacker-controlled bytes.

From File Write to SSTI

The application used Jinja templates. I built a minimal valid PDF and appended ZZ{{7*7}}ZZ. When ZZ49ZZ started appearing on pages, I knew I had overwritten a shared layout partial.

{{ cycler.__init__.__globals__.os.popen("id").read() }}

The response returned uid=0(root).

The Worker Problem

The application ran under uWSGI with multiple workers. Different requests could hit different workers, and each could have a different copy of the poisoned template. Reading command output directly became a coin flip.

The fix was to make the payload write the result into the application's static directory instead of printing it. Now it only took one successful render by any worker to create the files.

Almost every stage depended on noticing a small implementation detail in the previous one. The first bug did not give me the flag directly. It gave me the bot's identity, which gave me the upload feature, which gave me file write, which gave me SSTI, which finally gave me code execution.
