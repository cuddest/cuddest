The challenge description was already pointing in the right direction. The riddle talked about titles, inherited templates, and "his own voice will betray him". That sounded like template injection at first, but the inheritance wording made me suspect a prototype pollution chain behind it.

First Attempts

The application was an Express site with a notes form and an /admin page that returned 403.

Three details mattered:

  1. The admin check was simply req.cookies.admin === 'true'
  2. The application used a custom query parser that walked dotted keys — __proto__.x=y could reach Object.prototype
  3. EJS was pinned to 3.1.6, which still used outputFunctionName during compilation and inserted it directly into the generated function

Templates were not cached, so every render recompiled them and picked up the polluted value.

Why JSON Was a Dead End

My initial tests used JSON because __proto__ is the obvious starting point. That did not work because JSON.parse does not mutate Object.prototype. The vulnerable path was the query parser instead.

The Prototype Pollution Chain

The payload polluted the inherited outputFunctionName property. The chain was:

URL query parameter
        ↓
Custom parser
        ↓
Object.prototype pollution
        ↓
outputFunctionName inherited by EJS
        ↓
EJS code generation
        ↓
JavaScript execution

The Payload

The final request was a single GET request:

/?__proto__.outputFunctionName=x;var r=require('child_process').execSync('printenv').toString();__append(r);var y

The polluted value was inserted into the generated function, and require('child_process').execSync() gave me command execution. Because the same request both polluted the object and rendered the page, the command output came directly back in the HTTP response.

The important lesson here was that prototype pollution was not the final impact by itself. The interesting question is always: which polluted property is later consumed, and what does the consumer do with it?
