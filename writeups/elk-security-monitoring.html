ELK Home SOC — Containerized Security Monitoring with the Elastic Stack

A reproducible security monitoring platform, not a logging demo. Web, application, SSH and Windows telemetry enters one pipeline through Filebeat and Winlogbeat, is normalized in Logstash, indexed in Elasticsearch, investigated in Kibana, and evaluated by a lightweight detection engine — in pure simulation, real endpoint, and hybrid deployments.

01

Introduction

Modern systems produce an enormous amount of telemetry. Web servers record every request, applications record user activity, Linux machines record authentication events, and Windows systems generate detailed security logs. The first challenge I ran into was not collecting those logs — it was turning them into information that can be searched, correlated, detected, and investigated.

The first version of this project was a handful of unrelated log files. Each source had its own format, its own location, and its own idea of what a timestamp was. I chose to build a small SOC-style workflow around the Elastic Stack so that every source entered the same pipeline:

Collect telemetry↓ Normalize & enrich↓ Store & index↓ Detect suspicious activity↓ Investigate↓ Build an incident timeline

Logs alone are not a monitoring platform. The value comes from transforming telemetry into structure, structure into context, and context into detections that an analyst can actually investigate.

02

The central idea

This became the defining decision of the whole project. Rather than building separate tooling for each source, I wanted one security pipeline that accepts telemetry from many places. Synthetic generators, Docker services, and real endpoints all feed the same backend — because the pipeline only cares that an event can be represented consistently.

One security pipeline, multiple telemetry sources.

Synthetic Docker Real Linux Real Windows
↓
Logstash Elasticsearch Kibana

Simulation, real endpoint collection, and hybrid deployments all share this backend. Adding a real endpoint later is a configuration change, not a redesign.

The reason for keeping simulation mode was reproducibility. A security lab is far more useful when you can clone it, start it, generate the same activity, and reproduce the same investigation — without depending on external infrastructure. Real endpoint integration adds the realism that synthetic data cannot provide, and the architecture supports both at once.

03

Project goals

I set five objectives before writing any configuration, and every design decision in this project traces back to one of them:

Centralized collection

Treat every log source as part of one telemetry stream instead of managing each independently.

Consistent structure

Normalize events so different systems can be investigated together, not in silos.

Real detections

Go beyond dashboards — actually detect suspicious patterns and produce alerts.

Reproducibility

Clone it, start it, generate the same activity, and reproduce the same investigation.

Extensible

Evolve from synthetic generators toward real Linux and Windows endpoints without redesigning the backend.

The resulting architecture had to satisfy five requirements:

ReproducibleSecureSearchableDetection-orientedExtensible to real endpoints

04

Why this architecture

Each layer was chosen deliberately, and knowing the reasoning makes the pipeline easier to extend.

Docker

Reproducibility and isolation. The whole lab — including the Elastic Stack — spins up from docker compose, so every service is identical on any machine.

Filebeat / Winlogbeat

Dedicated endpoint collection. Agents run where the logs live, tail the right files, and forward events without the endpoint needing to know anything about the backend.

Logstash

The normalization boundary. This is where raw lines become structured, typed, enriched events — the single place that defines how the rest of the platform sees telemetry.

Elasticsearch

Indexed search and aggregation. Structured fields turn raw files into queryable data, which is the foundation for both dashboards and detection.

Kibana

Investigation and visualization. The analyst-facing surface: dashboards to spot anomalies, Discover to dig into the events underneath.

Synthetic generators

Reproducible test scenarios. Generators produce SSH failures, Windows logon events, web scans and error bursts on demand, so detections can be tested repeatedly.

Real endpoint integration

Practicality and realism. The same backend accepts telemetry from real machines, moving the lab from demonstration toward production-style collection.

Why the Elastic Stack?

The Elastic Stack was a natural fit because it separates the stages of the pipeline instead of squeezing collection, parsing, storage and visualization into one monolith. Each component has one clear job, which makes the whole system easier to reason about and easier to extend.

This separation is what makes the simulation → real endpoint migration cheap. Replacing a simulated Windows source with a real Windows endpoint does not require redesigning Elasticsearch or Kibana — the source changes while the downstream pipeline stays the same.

07

Data sources

The lab intentionally mixes real and synthetic telemetry. The badges make the distinction explicit, because simulated data must never be mistaken for genuine production telemetry.

Live in the lab

Nginx

Real web access logs — source IP, method, path, status, bytes, user agent, timestamp. An actual Nginx instance runs inside the environment, so this is genuine application telemetry, not a generator.

Live in the lab

Flask application

Structured JSON request events from a small application behind Nginx. Exposes /api/health, /api/products, /api/cart, /api/checkout, /api/login, /api/admin, /api/error and /api/slow — controlled endpoints for security testing alongside realistic application telemetry.

Synthetic — reproducible

SSH

A generator produces realistic authentication events on demand — failed logins, success, and targeted-user patterns. An optional container can instead run a real sshd to generate genuine authentication activity.

Synthetic — reproducible

Windows

A generator emits structured security events representing common logon events — notably 4624 (successful logon) and 4625 (failed logon) — so authentication scenarios can be reproduced with no Windows machine present.

Optional real integration

Linux endpoint

A real machine runs Filebeat locally and ships its logs into the lab. This is where the simulation architecture extends to production-style collection.

Optional real integration

Windows endpoint

A real Windows host runs Winlogbeat, which reads Windows Event Logs locally and forwards them to Logstash. The repository ships a reference winlogbeat.yml for configuring this.

08

Collection layer

The collection layer moves events from their source into the processing pipeline. Filebeat handles Linux, web and application-style log collection. Winlogbeat reads Windows Event Logs.

The key design principle: the downstream pipeline should not care whether an event came from a generator, a Docker container, a Linux machine or a Windows machine. As long as the event can be represented consistently, the rest of the system processes it the same way. This is what makes the simulation → real endpoint migration a configuration change rather than a redesign.

In simulation, the agents tail locally generated files. On real endpoints, the agents run on the machines themselves and ship events over the network (optionally over TLS) to Logstash. The reference configuration for that lives in the repository — endpoints do not read the lab's configuration remotely.

09

Logstash — the processing layer

Logstash is the normalization boundary of the project. Raw telemetry enters as strings and leaves as structured events. Click each stage to see what it does.

Beats agents connect and stream events in over the Beats protocol. Logstash listens as the ingestion endpoint of the whole pipeline.

Raw lines arrive as strings. A pattern such as 172.23.0.1 - - "GET /products HTTP/1.1" 200 is parsed into named fields: source.ip, http.request.method, url.path and http.response.status_code.

Different systems represent timestamps differently. The pipeline converts them into a common @timestamp, which is essential for time-based queries, timelines, dashboards and event correlation.

A field such as "404" is converted into the numeric value 404, enabling proper aggregations and comparisons.

Source IP addresses can be enriched with additional context, such as geographic information, when the relevant data is available.

Events are routed to dedicated indexes by source — logs-nginx-*, logs-application-*, logs-ssh-*, logs-windows-* — while security alerts are stored separately in security-detections-*.

The processed, normalized events are indexed into Elasticsearch, where they become searchable and aggregable.

10

Raw event → normalized event

One of the most important design goals was consistency. Different systems naturally use different field names — source_ip, src_ip, client_ip, remote_ip — even though they all mean the same thing. Without normalization, correlation becomes impossible.

RAW TELEMETRY ↓ Collector ↓ Logstash ↓ Normalize / Enrich ↓ STRUCTURED EVENT

Raw log

172.23.0.1 - - "GET /admin HTTP/1.1" 404 - "-" "curl/8.0"

Normalized event

@timestamp 2026-08-19T00:00:00Z source.ip 172.23.0.1 http.request.method GET url.path /admin http.response.status_code 404 event.outcome failure

Structured fields are what make correlation possible. Because SSH and Windows telemetry both expose source.ip, user.name and @timestamp, the same investigation methodology works across both sources — and a timeline can combine them into a single story.

11

Elasticsearch

Elasticsearch stores processed events as indexed documents. Instead of searching massive raw log files, an analyst can query structured fields directly:

event.outcome: failureall failed events
source.ip: 185.234.72.45everything from one address
event.code: 4625Windows failed logons

The data is also suitable for aggregation — counting authentication failures, grouping by source.ip, grouping by user.name. This lets the platform move from raw events to patterns, which is the foundation for detection.

12

Kibana

Kibana is the analyst-facing interface, with two primary uses.

Discover

Event-level investigation. An analyst searches source.ip:185.234.72.45 and walks chronologically through the telemetry, inspecting every relevant event around an alert.

Dashboards

A higher-level view. The project is designed around dashboards for a SOC overview, authentication, web security, Windows security, application health and monitoring-pipeline health — tracking total events, auth failures/successes, HTTP 4xx/5xx, top source IPs, top users and events over time.

The dashboard is not meant to replace investigation — it drives it: identify an anomaly, drop into Discover, and investigate the events underneath.

13

Detection engineering

A monitoring platform is much more useful when it can recognize suspicious behavior. The project includes a lightweight detection engine whose logic focuses on patterns rather than single events — repeated failures, threshold crossings, and sequences that look like compromise.

Telemetry↓ Detection↓ Alert↓ Investigation

When a detection triggers, the engine creates a structured alert stored separately from ordinary telemetry in security-detections-*, carrying the rule name, source and severity so it can be triaged like any other security event.

14

Detections

Five representative detections demonstrate the engine. Each entry follows the same shape — source, signal, logic, output, investigation — so it reads like a miniature detection-engineering document. Open a card to expand it.

SSH brute force

Source — SSH authentication events from the generator or a real sshd.

Signal — repeated failures from the same source.ip within a short window.

Logic — count failed SSH events, group by source.ip, apply a time window, compare against a threshold.

Output — a structured security alert for the offending address.

Investigation — pivot on source.ip, list the targeted users, and check whether any failure was followed by a success.

Windows brute force

Source — Windows security events — repeated 4625 (failed logon) events.

Signal — repeated 4625 events from the same source address.

Logic — same principle as SSH: count failed logons, group by source, apply window and threshold.

Output — a Windows brute-force alert.

Investigation — look for 4624 (successful logon) events from that source after the failures.

Authentication failure → success

Source — correlated SSH and/or Windows authentication telemetry.

Signal — repeated failures from the same source, then a successful login.

Logic — correlate failure bursts by source.ip against any subsequent outcome: success event from the same address.

Output — a high-priority investigation lead.

Investigation — ask who authenticated, from where, against which host, when the success happened, and what occurred immediately afterwards.

Web scanning

Source — Nginx access logs.

Signal — the same source.ip generating many 404 responses across sensitive or unusual paths — /admin, /.env, /wp-admin, /phpmyadmin.

Logic — count 4xx responses per source over a window, weighted toward sensitive paths.

Output — a web-scanning alert.

Investigation — enumerate the probed paths, compare against the application's real routes, and check for any later successful requests to those paths.

Application error bursts

Source — Flask application telemetry; the app exposes an endpoint that intentionally generates server errors.

Signal — an abnormal increase in HTTP 5xx responses (500, 502, 503).

Logic — monitor http.response.status_code aggregates over time for 5xx spikes.

Output — an application-health alert.

Investigation — correlate error spikes in time with authentication or web-scanning alerts; determine whether the cause is an exploit attempt or a real outage.

Attack simulation

One of the most useful features is that attack scenarios are reproducible. Instead of manually recreating each scenario, the generators produce the necessary telemetry with a single command. All of the following are deliberate, controlled lab scenarios:

SSH brute force

Repeated failed authentications from one or more source addresses.

Windows authentication failures

Bursts of 4625 events to reproduce logon guessing.

Failure → success

Failed attempts followed by a successful authentication.

Web scanning

Repeated suspicious paths such as /admin, /.env, /wp-admin.

Application error bursts

Intentional 5xx spikes from the Flask endpoint.

For example, a Windows failure scenario is generated with:

python3 generators/windows/generate_windows_events.py \
  --count 12 --mode failure

and a web scan with:

Investigation walkthrough

Once an alert fires, the project follows a basic SOC methodology. The goal is not to say "there were many failed logins" — it is to determine what happened, when, which system and account were involved, and what happened afterwards.

DetectionInitial evidenceSource identification Related eventsTimelineCorrelationAssessment

From alert to conclusion

The investigation below mirrors a real lab run: the SSH generator produced failures from 185.234.72.45, and the detection fired. Each step shows what an analyst would actually look at in Kibana.

  1. Detection. The brute-force rule triggers on repeated failures from 185.234.72.45 and writes an alert to security-detections-*.
  2. Initial evidence. The alert names the source and the pattern — see the generated events in section 15.
  3. Source identification. The analyst pins the address with source.ip:185.234.72.45.
  4. Related events. The same query across all indexes surfaces authentication, web and application activity touching that address.
  5. Timeline. Events are ordered chronologically to build the sequence below.
  6. Correlation. A successful authentication after the failures changes the assessment.
  7. Assessment. The analyst documents source, target, timing and impact.

Click each entry to inspect it — this is the timeline the analyst builds:

Another failed attempt from 185.234.72.45 against a system account.
Same source, same target account — the pattern is building.
A third rapid failure — this is no longer coincidence.
Fourth failure, still the same source IP and user.
The failures were followed by a successful login — the key escalation point.
Immediately after the success, application activity from the same source.
A request to an administrative endpoint — the post-compromise narrative completes.

The investigation then expands: search source.ip:185.234.72.45 and inspect nearby events to build the full timeline. An individual event may be harmless; a sequence of related events tells a much stronger story. That correlation is the core skill this walkthrough demonstrates.

Correlating across sources

The same methodology works on the Windows telemetry. A failed logon for user testfail (4625, status 0xc000006d — bad password) indexed on host DC01-PROD is the Windows equivalent of the SSH failures: it becomes interesting only when grouped with the surrounding 4624 successes. Both share the fields needed for that grouping — @timestamp, source/host, user and event.outcome.

17

Securing the platform

A security monitoring platform should itself be protected. I deliberately moved away from an unauthenticated development environment toward a hardened configuration — Elasticsearch authentication, TLS, restricted port exposure, dedicated service credentials, secret separation, and internal Docker networking.

The system collecting sensitive security telemetry should not itself become an easy target.

Development

  • Elasticsearch reachable on :9200, auth disabled
  • No TLS between components
  • Services exposed broadly
↓

Hardened

  • Elasticsearch authentication
  • TLS for component communication
  • Restricted port exposure
  • Dedicated service credentials
  • Internal Docker networking

The repository ships the development profile for reproducibility, and the hardened configuration is the documented production direction — the same architecture, with the security controls enabled.

Why Elasticsearch should not be public

Security telemetry may contain IP addresses, usernames, hostnames, authentication events, application activity and system information. Exposing Elasticsearch unnecessarily creates an additional attack surface. The intended access path is:

External user↓Kibana / controlled interface↓Elasticsearch

rather than exposing Elasticsearch :9200 directly to the internet.

18

Real endpoint integration

The project is not limited to Docker. A real Linux machine runs Filebeat locally and ships telemetry into the lab; a real Windows machine runs Winlogbeat locally and reads its Event Logs.

Linux

Linux↓Filebeat↓Logstash↓Elasticsearch

Filebeat runs on the endpoint itself. The repository provides the reference configuration; the endpoint does not remotely read the lab's config.

Windows

Windows Event Log↓Winlogbeat↓Logstash↓Elasticsearch

Winlogbeat runs on the Windows host and forwards events (optionally over TLS). A reference winlogbeat.yml ships in the repository.

To be explicit about the boundary: the Windows machine runs Winlogbeat locally — it does not remotely read the GitHub repository, and the repository only provides the reference configuration. The same backend also continues to accept synthetic Windows events, so a hybrid deployment can mix real and simulated sources freely.

The lab's own data confirms the agent side of this design. The Windows events shown in section 10 were collected by a Winlogbeat agent identifying as DC01-PROD (version 8.13.0), the same version pinned in the project's configuration — the collection boundary is identical whether the source is simulated or real.

The same backend can therefore collect telemetry from Docker containers, Linux endpoints, Windows endpoints, servers and workstations — one pipeline, many sources.

Testing strategy

A security platform can fail at multiple layers — an alert not appearing could mean the generator failed, the agent failed, Logstash failed, parsing failed, indexing failed, or the detection itself failed. The project therefore tests layers independently:

01 · Infrastructure

Verify Docker configuration, services, health and networking — docker compose up then health-check each service.

02 · Data ingestion

Verify the path source → collector → Logstash → Elasticsearch, and confirm documents land in the right index.

03 · Detection

Run a known scenario and confirm the expected detection and alert in security-detections-*.

04 · Investigation

Confirm alert → search → correlation → timeline produces a coherent story.

05 · Persistence

Restart the stack and verify the indexed dataset survives docker compose down / up.

06 · Reset

Confirm the deliberate reset mechanism returns the lab to a fully clean state when needed.

The overall flow stays repeatable: start the stack, run health checks, generate normal traffic, run a scenario, confirm the detection in Kibana, investigate, and reset when required. The repository is the source of truth for the exact commands.

Persistence

Ephemeral containers are separated from persistent Elasticsearch data, so restarting the environment does not destroy the indexed dataset — and a deliberate reset mechanism exists for when a completely clean lab is required.

Limitations

This environment is intentionally a lab rather than a full production SOC.

Single-node Elasticsearch

No highly available cluster — this is a single-node deployment.

Synthetic telemetry

Simulation mode is synthetic and must not be mistaken for genuine enterprise traffic.

Simplified detection

The engine demonstrates core detection concepts but does not replace a mature SIEM correlation engine.

Limited coverage

Primary focus on Linux, Windows, Nginx and application telemetry; more sources can be added later.

23

Lessons learned

The biggest lesson from this project is that centralized logging alone does not create a security monitoring platform. A raw log line is only the beginning.

  • Normalization makes events comparable.
  • Aggregation reveals patterns.
  • Detections highlight suspicious behavior.
  • Correlation gives context.
  • Investigation turns those events into an explanation of what actually happened.

Reproducibility matters just as much. A security lab should not depend entirely on external infrastructure. Synthetic generators make it possible to repeatedly test detections under controlled conditions, while real endpoint integrations let the same architecture evolve toward realistic deployments.

24

Conclusion

The goal of this project was not simply to deploy Elasticsearch, Logstash and Kibana. It was to build a small environment that demonstrates the complete lifecycle of security telemetry.

Telemetry↓ Structure↓ Context↓ Detection↓ Investigation

Events from applications, web infrastructure, Linux and Windows systems enter one pipeline through dedicated collection agents. Logstash parses, normalizes and enriches them; Elasticsearch makes them searchable; Kibana lets an analyst investigate them; and a detection engine turns patterns into alerts that feed a structured incident workflow.

The architecture is intentionally flexible. A developer runs everything locally with synthetic data. A security engineer connects real Linux or Windows endpoints. A hybrid deployment combines both. That one backend demonstrates security monitoring, systems administration, Docker, the Elastic Stack, endpoint telemetry, detection engineering, threat hunting and incident investigation — and, most importantly, that collecting logs is only the beginning.
